# Hearth v0.4 (Ticked Rooms) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rooms can run in `mode = "ticked"`: a fixed 5–20 Hz simulation that runs while players are connected and stops when they leave. Both SDKs get snapshot interpolation, and a top-down "arena" sample shows client-side prediction from a shared Rust logic crate compiled into a Godot GDExtension.

**Architecture:** Task 1 settles the spec's open question first. A deployed benchmark compares an alarm-driven tick against a held-open in-isolate loop and records the choice in an ADR. The pure runtime does not depend on that choice: it exposes `next_wake()` and a fixed-step `tick()`, and only the Durable Object adapter's driver differs. Intents are buffered and applied at the start of the next tick, so the server and the predicting client step the same inputs at the same `dt`. Sync cost drops because the public part of the view is diffed once per pass, and only `#[sync(owner)]` fields are diffed per client. That change also benefits event rooms. Interpolation and prediction live in the sans-IO client core, so every SDK shares them.

**Tech Stack:** As before. The benchmark uses Cloudflare's GraphQL Analytics API to count billed requests.

**Spec:** [`Hearth a Rust framework for Durable Object game servers.md`](../../../Hearth%20a%20Rust%20framework%20for%20Durable%20Object%20game%20servers.md), sections Target games (Ticked mode), Room lifecycle step 3, Design rules (persist every N ticks), Client SDKs (Prediction), and Open questions (alarm granularity). **Builds on:** every earlier plan ([v0.1](2026-10-25-hearth-v0.1-event-rooms.md), [v0.2a](2026-10-25-hearth-v0.2a-reconnect-godot-codegen.md), [v0.2b](2026-10-25-hearth-v0.2b-unity.md), [v0.2c](2026-10-25-hearth-v0.2c-admin.md), [v0.3a](2026-10-25-hearth-v0.3a-rpc-players-matchmaking.md), [v0.3b](2026-10-25-hearth-v0.3b-auth-limits-cost.md)). Names this plan does not redefine are as defined there.

## Global Constraints

- All earlier Global Constraints still apply.
- Ticked mode (spec): an alarm-driven fixed tick of **5–20 Hz** while players are connected. It is billed wall-clock while ticking and stops when the room empties. A room picks its mode at compile time. Anything above about 20 Hz goes to Handoff, and the compile error says so.
- State is persisted every N ticks in ticked mode (spec), with the default `persist_every = 20`. The state is also persisted when ticking stops, on dispose, and before an admin inspect.
- Prediction (spec): optional, using the game's shared logic crate compiled into the same GDExtension. **This plan ships the Godot prediction sample.** Unity gets interpolation only. Unity prediction (the shared logic crate in the native plugin) is the next plan.
- Protocol stays at version 1. `PATCH` and `ACK` gain the **optional** fields `tick: Option<u64>` and `t: Option<u64>` (server ms at the tick). Event rooms leave them out, and decoders already ignore unknown fields. Update `docs/protocol.md`.
- Fixed timestep: `on_tick` always receives `dt = 1 s / tick_hz`. A wake runs at most **3** catch-up ticks. Missed ticks beyond that are dropped and logged.
- Shared logic must be deterministic in practice: use only `+ - * /`, `sqrt` and comparisons on `f32`, with no transcendental functions or platform intrinsics. Mispredictions are reconciled anyway, but the sample should rarely produce them.
- **Out of scope:** lag compensation and rollback (a spec non-goal), Unity prediction, delta compression beyond the existing diff, Handoff (v0.5).

## Review Focus

1. **Catch-up spiral.** After a 2 s stall (eviction, GC or a slow handler), the room must run at most 3 catch-up ticks, log `tick_dropped`, and resume on schedule. It must never run 40 ticks back to back. Tests are in Task 3.
2. **Zombie ticking.** A room whose players have all disconnected (held seats included), or that has been disposed, must stop ticking and stop scheduling wakes, because ticking is billed wall-clock. It restarts on the next connect or resume. Tests are in Tasks 3 and 4.
3. **Intents between ticks.** They must be applied at the next tick, in arrival order, exactly once, and ACKed with that tick. Intents buffered when the isolate is evicted are lost, and the client must see them as `IntentsUnconfirmed`, never as applied. Tests are in Task 3.
4. **Interpolation edge cases.** Out-of-order snapshots, a server clock jump, a 2 s gap, and a single snapshot. Sampling must never extrapolate more than one tick past the newest snapshot, and then holds. Tests are in Task 5.
5. **Prediction divergence.** When the server disagrees (another player blocks you), the predicted avatar must converge to the authoritative position within 200 ms. A client that sends invalid input (`dir = [5, 0]`) must have no effect beyond `[1, 0]` on the server. Tests are in Task 8.

### Task 1: Tick-driver benchmark and ADR

**Files:**
- Create: `bench/tick-bench/Cargo.toml`, `src/lib.rs`, `wrangler.toml`, `run.mjs`, `README.md`
- Create: `bench/diff-bench/` (a native binary)
- Create: `docs/adr/0001-tick-driver.md`

**Interfaces:**
- Consumes: `worker` only. This is a standalone Worker, kept off the Hearth runtime so it measures the platform.
- Produces:
  - DO class `AlarmTicker` handles `POST /start?hz=H&secs=S`. On each `alarm()` it records `Date.now()`, burns a configurable `work_us` of CPU (a busy loop on `Date.now()`), and calls `set_alarm(start + n * period)` (an absolute schedule, so drift does not accumulate). It stops after `S` seconds.
  - DO class `LoopTicker` does the same with `wasm_bindgen_futures::spawn_local` looping on `worker::Delay` for the remaining time to the next scheduled tick.
  - Both accept one hibernatable WebSocket. The client keeps it open, which mimics a connected player, and the DO sends a 1-byte message per tick so client-side jitter can be measured as well.
  - `GET /stats` → `{ "ticks", "expected", "missed", "interval_err_ms": {"p50","p95","p99","max"}, "evicted": bool }`. `evicted` is true when the in-memory start marker vanished mid-run.
  - `run.mjs --url <deployed> --hz 10,20 --secs 600 --work-us 0,2000` runs every combination for both classes in parallel DOs, holds the WebSockets, and writes `bench/tick-bench/results.json` with the server stats and client-side receive jitter. With a Cloudflare API token and account ID in the env, it also queries the GraphQL Analytics API for the requests and duration billed per DO class over the run window.
  - `diff-bench` (native, `std::time::Instant`): for clients ∈ {4, 16, 64} and state sizes ∈ {1, 10, 100} KB, with 10% of leaf fields changed per pass, it measures the ms per pass of (a) per-client full view + diff (current) and (b) one public diff + per-client owner-field diff (Task 2), and prints a table.
  - ADR decision rule. Pick the first option that holds:
    1. **Alarm** if, at 20 Hz with `work_us = 2000`, server `p99 interval_err_ms ≤ 12.5` (25% of the 50 ms period), `missed / expected ≤ 1%`, and there were no evictions.
    2. Otherwise **Loop**, if it meets the same bar.
    3. Otherwise lower the supported maximum `tick_hz` to the highest tested rate that meets the bar for either driver, and choose that driver.

    The ADR records the numbers, the billed requests and duration per driver per room-hour, the choice, and the resulting maximum Hz. It also updates the spec's Open questions note by recording the answer in the ADR; do not edit the spec itself.

### Task 3: Ticked mode in the runtime

**Files:**
- Modify: `crates/hearth-server/src/room.rs`, `src/runtime.rs`, `src/ctx.rs`; `crates/hearth-protocol/src/frame.rs`, `docs/protocol.md`

- Modify: `crates/hearth-test/src/lib.rs` (`ticks(&self) -> u64`, `stall(&mut self, d)`)
- Test: `crates/hearth-test/tests/ticked.rs`

**Interfaces:**
- Consumes: Task 2, the timers and alarm path, v0.2a held seats, and v0.2c logs.
- Produces:
  - `Mode::{Event, Ticked}`. `RoomConfig` gains `const TICK_HZ: u8 = 0;` and `const PERSIST_EVERY: u32 = 20;`. `Room` gains `async fn on_tick(&mut self, ctx: &mut Ctx<Self>, dt: Duration) -> Result<()> { Ok(()) }`. `Ctx` gains `fn tick(&self) -> u64`, which is 0 in event mode.
  - `Frame::Patch { seq, ops, tick: Option<u64>, t: Option<u64> }` and `Frame::Ack { state_seq, intent_seqs, tick: Option<u64> }`, both `#[serde(default, skip_serializing_if = "Option::is_none")]`. `ClientCore` exposes `last_tick(&self) -> Option<(u64 /*tick*/, u64 /*t*/)>`.
  - Ticked runtime rules:
    - **Ticking** is true while at least one *connected* client exists. Held seats and admin tails do not count.
    - **Start.** On the transition to ticking, set `tick_origin_ms = now` and `next_tick_ms = now + period`. The tick counter continues from the persisted `hearth_meta.tick` (default 0).
    - **Intents.** While ticking, the decoded `INTENT`s are appended to an in-memory `pending: Vec<(PlayerId, u32 seq, Intent)>` and not run at once. A frame that cannot be decoded still gets an immediate `BAD_INTENT`.
    - **`tick()`.** Let `due = floor((now - next_tick_ms) / period) + 1`. Run `min(due, 3)` steps. Log `{"hearth":"tick_dropped","n":due-3}` when `due > 3`. Each step is one handler pass:
      1. drain `pending` and run `on_intent` for each, in arrival order, with rollback per intent as in v0.1;
      2. run `on_tick(dt = period)` (on `Err`, roll back the tick's own changes, log `handler_error`, and continue);
      3. increment `tick`.

      After the steps, set `next_tick_ms += steps_due * period`, so the schedule stays absolute and skipped ticks are skipped. Then flush one `PATCH { tick, t: now }` per client and one `ACK { tick }` per sender.
    - **Persistence.** Persist when `tick % PERSIST_EVERY == 0`, when ticking stops, on dispose, and before `inspect`. Persist the `tick` into `hearth_meta` together with the state.
    - **Stop.** When the last connected client leaves, drops or is kicked, run the pending intents, persist, and set `next_tick_ms = None`.
    - **Wake.** `pub fn next_wake(&self) -> Option<u64>` returns the minimum of the next timer, the outbox retry and `next_tick_ms`. `alarm()` calls `tick()` when it is due and then fires the timers, so the alarm driver needs nothing more. `pub async fn tick_if_due(&mut self)` is for a loop driver.
    - **Overrun.** When the pass takes more than one period of wall time (measured with `host.now_ms()`), log `{"hearth":"tick_overrun","ms":..}`.
    - **Event mode** is unchanged: none of these rules apply, and `tick` and `t` are left out.
  - `TestRoom::advance` already drives the alarm, so it now drives ticks too. `stall(d)` moves the clock forward by `d` **without** firing the alarm, then fires it once, which simulates a late wake.

Test room `Mover` (`mode = Ticked`, `TICK_HZ = 10`, `PERSIST_EVERY = 5`): `State { #[sync] pos: SyncMap<PlayerId, i32>, #[sync] vel: SyncMap<PlayerId, i32> }`, `Intent = SetVel(i32)` (clamped to -1..=1), and `on_tick` adds `vel` to `pos` for each player.

### Task 5: Clock sync and interpolation in the client core

**Files:**
- Create: `crates/hearth-client/src/interp.rs`, `tests/fixtures/interp_cases.json`, `tests/interp.rs`
- Modify: `crates/hearth-unity/src/lib.rs` (FFI and wasm exports), `include/hearth_unity.h`

**Interfaces:**
- Consumes: `ClientCore::last_tick` and the state `Value`.
- Produces:
  - `pub struct ClockSync`, with methods `new() -> Self`, `fn observe(&mut self, server_t: u64, local_recv_ms: u64)`, `fn server_now(&self, local_ms: u64) -> Option<u64>`. It estimates the offset as the **max** of `(server_t - local_recv)` over the last 32 samples (the sample with the least delay). When the newest sample differs from the estimate by more than 1000 ms, it resets the window, which handles a server clock jump (Review Focus 4).
  - `pub struct Interpolator`, with methods `new(tick_hz: u8) -> Self`, `fn track(&mut self, path: Vec<Value>)`, `fn on_patch(&mut self, state: &Value, server_t: u64)`, `fn sample(&self, path: &[Value], render_t: u64) -> Option<Value>`, `fn render_time(&self, clock: &ClockSync, local_ms: u64) -> Option<u64>`.
    - `on_patch` records a snapshot of each tracked path. It keeps snapshots for 1 s and **discards** any snapshot whose `server_t` is not newer than the newest one kept (out-of-order).
    - `render_time` is `server_now - interp_delay`, where `interp_delay = 2 × period`.
    - `sample` brackets `render_t` between two snapshots. Numbers are lerped. Arrays of numbers of equal length are lerped per element. Anything else takes the older snapshot's value.
    - Past the newest snapshot, it extrapolates linearly for at most one period and then holds the value. Before the oldest, it returns the oldest. With a single snapshot, it returns that snapshot. When the path is missing from the bracketing snapshots, it returns `None`.
  - Fixture `interp_cases.json`: `[{ "name", "tick_hz", "snapshots": [[server_t, value]], "render_t", "expect": value | null }]`. It covers mid-bracket lerp, array lerp, a string (step), extrapolation capped at one period, a hold beyond that, before the first snapshot, a single snapshot, out-of-order (discarded), and a 2 s gap (lerp across the gap).
  - FFI/wasm: `hearth_interp_new(tick_hz) -> *mut`, `_free`, `_track(path_json)`, `_on_patch(state_json, server_t)`, `_sample(path_json, render_t) -> HearthBuf` (JSON, or empty), `hearth_clock_new/_free/_observe/_server_now -> i64 (-1 = none)`, and the matching `wasm_bindgen` wrappers.

### Task 8: Prediction: the `Logic` trait, `Predictor`, and the Godot arena sample

**Files:**
- Create: `crates/hearth-client/src/predict.rs`, `tests/predict.rs`
- Modify: `crates/hearth-godot/src/lib.rs` (`predictor!` macro)
- Create/complete: `examples/arena-logic/src/lib.rs`, `examples/arena-godot-ext/` (cdylib), `examples/arena-godot/` (project, `main.gd`, `tests/predict_smoke.gd`)
- Modify: `crates/hearth-godot/src/lib.rs` (debug latency injection)
- Create: `docs/ticked.md`

**Interfaces:**
- Consumes: Tasks 3–6, plus `ClientEvent::Acked { intent_seqs, .. }` / `IntentsUnconfirmed`.
- Produces:
  - `pub trait Logic { type State: DeserializeOwned + Clone; type Input: Serialize + Clone; fn step(state: &mut Self::State, inputs: &[(PlayerId, Self::Input)], dt: Duration); }`
  - `pub struct Predictor<L: Logic>`, with these methods:
    - `new(me: PlayerId, tick_hz: u8) -> Self`
    - `fn input(&mut self, seq: u32, input: L::Input)`: records the input and steps the local predicted state one tick with `[(me, input)]`.
    - `fn on_authoritative(&mut self, server_state: &Value, acked: &[u32])`: drops the inputs with `seq <= max(acked)`, rebuilds the predicted state from the server state, and replays the remaining inputs in order, one step each.
    - `fn on_unconfirmed(&mut self, seqs: &[u32])`: drops those inputs.
    - `fn predicted(&self) -> &L::State`
  - Each tick, the dev sends one `Move` intent and calls `input` with the same seq (`Hearth.send_intent` returns it).
  - `arena_logic`: `pub struct Arena;` implements `Logic` with `State = ArenaState { avatars: BTreeMap<String, Avatar> }` (it mirrors the room's synced shape, and deserialises from the client view) and `Input = Move { dir: [i8; 2] }`. `step` clamps `dir`, moves at 4 units/s, clamps to the 0..=20 arena bounds, and resolves avatar-avatar overlap by pushing back (this is what can cause mispredictions). The server `Arena` room's `on_tick` calls the same `step` with the pending moves of every player (Task 4).
  - `hearth_godot::predictor!(ArenaPredictor, arena_logic::Arena)` generates a `#[derive(GodotClass)]` class with `input(seq: int, input: Variant)`, `predicted_state() -> Dictionary`, and automatic wiring through `attach(hearth_node: Node)`, which connects to the `acked`, `patched` and `intents_unconfirmed` signals.
  - `examples/arena-godot-ext`: a cdylib that depends on `hearth-godot` and `arena-logic` and calls the macro. Its `.gdextension` *replaces* the stock addon's library in this project, with the same entry symbol, so `HearthNative` is still registered.
  - Rendering in the sample:
    - The player's own avatar is drawn from `predicted_state()`.
    - Other avatars use `Hearth.interpolator([["avatars","*","pos"]])`.
    - When the drawn predicted position and the newest authoritative position differ by more than 0.01, the drawn position is smoothed toward the corrected prediction at 15%/frame. A difference above 2 units snaps.
  - Debug-only `HearthNative.debug_latency_ms: int` delays outgoing sends and incoming frames by that amount, for testing.

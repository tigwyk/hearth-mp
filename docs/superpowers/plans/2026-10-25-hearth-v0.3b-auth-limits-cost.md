# Hearth v0.3b (Auth Providers, Rate Limits, `hearth cost`) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Players sign in with a JWT from the dev's own backend, a Steam session ticket, an itch.io API key or a Discord OAuth code. Each one is exchanged at the gateway for the existing Hearth session token. The gateway rate-limits per IP and per player, room intent caps become configurable, and `hearth cost` estimates the monthly Cloudflare bill before launch.

**Architecture:** Every provider is a pure *verify* step that turns an external credential into an `Identity { player_id, provider, display_name }`. The existing HMAC token is then issued for that identity, so the connect path and the rooms keep a single verification path. Provider HTTP calls go through a small `Fetcher` trait, so each provider is tested natively against canned upstream responses. JWT signatures use HS256 through `hmac` (already a dependency) and RS256/ES256 through the Workers WebCrypto API. Using WebCrypto adds no crypto crate to the Wasm bundle, which keeps down the bundle size the spec flags as an open question. Rate limiting uses the Workers Rate Limiting binding. `hearth cost` is a pure function over a versioned pricing table.

**Tech Stack:** As before, plus `web-sys` (features `SubtleCrypto`, `CryptoKey`) for WebCrypto. No new crates in the CLI.

**Spec:** [`Hearth a Rust framework for Durable Object game servers.md`](../../../Hearth%20a%20Rust%20framework%20for%20Durable%20Object%20game%20servers.md), sections Auth, Abuse limits and Cost model. **Builds on:** [v0.1](2026-10-25-hearth-v0.1-event-rooms.md), [v0.2a](2026-10-25-hearth-v0.2a-reconnect-godot-codegen.md), [v0.2b](2026-10-25-hearth-v0.2b-unity.md), [v0.2c](2026-10-25-hearth-v0.2c-admin.md) and [v0.3a](2026-10-25-hearth-v0.3a-rpc-players-matchmaking.md). Names this plan does not redefine are as defined there.

## Global Constraints

- All earlier Global Constraints still apply.
- Providers (spec): anonymous device ID, signed JWT from the dev's own backend, Steam session ticket, itch.io, Discord OAuth. Rooms never see raw credentials (spec): only the `PlayerId`, provider and display name reach a room.
- Abuse limits (spec): gateway rate limiting per IP and per player, per-room intent caps with configurable kick thresholds, and the max message size enforced before deserialisation (already in place since v0.1).
- `hearth cost` estimates monthly spend from CCU, room size, intents/sec and tick rate (spec). WebSocket incoming messages are billed at a 20:1 ratio to requests (spec).
- **Prices are data, not code.** `crates/hearth-cli/pricing.toml` holds every price and included allowance, an `as_of` date and the source URLs (the spec's "Durable Objects pricing" link plus the Workers pricing page). On the day Task 5 starts, refresh every number from those pages. `hearth cost` prints `as_of` in its output.
- Player IDs are namespaced per provider: `anon_`, `jwt_`, `steam_`, `itch_` and `discord_`. A provider can never mint an ID in another provider's namespace.
- Display names: at most 64 Unicode scalar values after trimming, with Unicode control characters (Cc) and line/paragraph separators removed. When empty, there is no name.
- **Out of scope:** linking accounts across providers, refresh tokens (re-authenticate after the 24 h TTL), the Discord browser redirect flow (only the code exchange is built; it covers Discord Activities and any client that already has a code), Steam display names (no `GetPlayerSummaries` call), and ticked-mode runtime (v0.4). `hearth cost` already models ticked mode, because the spec asks for tick rate.

## Review Focus

1. **JWT validation holes.** `alg: none`, an HS256 token signed with the RS256 public key (algorithm confusion), a missing `exp`, an expired token, `nbf` in the future, and a wrong `iss` or `aud`. Each must be rejected with 401. Tests are in Task 2.
2. **Impersonation across namespaces.** A JWT whose `sub` is `steam_7656…`, or a `sub` with `/`, CR/LF or 200 characters. The resulting ID is always `jwt_`-prefixed, and an invalid `sub` is rejected. Tests are in Tasks 1 and 2.
3. **Display names carrying control characters, CR/LF (header injection) or a 10 kB string.** They must be sanitised before they go into the token or the `X-Hearth-Display-Name` header. Tests are in Task 1.
4. **Provider upstream down, slow or returning HTML.** The gateway must return `502 {"error":"<provider> unavailable"}` within its 5 s timeout, and must never issue a token on anything but a verified OK. Tests are in Task 3.
5. **Rate limits locking out shared IPs.** Under CGNAT or on a school network, many players share one IP. The per-IP default must be generous (300/60 s) and the per-player limit tight. Every 429 carries `Retry-After`. A missing binding (local dev) means no limiting, not an error. Tests are in Task 4.

### Task 2: JWT provider (HS256, RS256, ES256, JWKS)

**Files:**
- Create: `crates/hearth-gateway/src/providers/jwt.rs`, `src/webcrypto.rs`
- Test: `crates/hearth-gateway/tests/jwt.rs` (native: claims + HS256), `examples/tictactoe/e2e.mjs` (RS256/ES256 through a local JWKS)

**Interfaces:**
- Consumes: Task 1.
- Produces:
  - `pub struct JwtConfig { pub issuer: String, pub audience: String, pub keys: JwtKeys, pub name_claim: Option<String> /* e.g. "name" */ }` and `pub enum JwtKeys { Hs256 { secret_env: &'static str /* ≥32 bytes, else 500 at startup check */ }, Jwks { url: String } }`.
  - Request body: `{"jwt": "<compact JWS>"}`.
  - `pub fn parse(jwt: &str) -> Result<(Header, Claims, Vec<u8> /*signing input*/, Vec<u8> /*sig*/), ProviderError>`, plus the pure function `pub fn check_claims(c: &Claims, cfg: &JwtConfig, now_s: u64) -> Result<(), ProviderError>`. The rules:
    - `exp` is required and checked with 60 s leeway.
    - `nbf`, when present, is checked with 60 s leeway.
    - `iss` must equal `cfg.issuer`.
    - `aud` (a string or an array) must contain `cfg.audience`.
    - `sub` is required.
  - Allowed algorithms are bound to the key type, which closes algorithm confusion:
    - `Hs256` keys accept only `alg == "HS256"`.
    - JWKS keys accept only the `alg` the JWK declares, or when it declares none, `RS256` for `kty: "RSA"` and `ES256` for `kty: "EC"` with `crv: "P-256"`.
    - `none` and any other value are always `Rejected`.
    - With JWKS, the `kid` in the header is required and must match a key.
  - JWKS cache: in-memory per isolate with a 10-minute TTL. When `kid` misses the cache, refetch once at most every 60 s, so a forged `kid` cannot hammer the JWKS URL. A JWKS fetch failure with no cached keys is `Upstream`.
  - `webcrypto::verify(alg: &str, jwk: &Value, signing_input: &[u8], sig: &[u8]) -> Result<bool, String>`. It uses `crypto.subtle.importKey("jwk", ...)` and then `verify`. RS256 is `RSASSA-PKCS1-v1_5` with SHA-256. ES256 is `ECDSA` with P-256 and SHA-256, and the JWS signature is already in the raw r‖s form that WebCrypto expects.
  - Identity: `namespaced("jwt", sub)`, with `display_name` = `sanitize_name(claims[name_claim])` when it is configured.

### Task 3: Steam, itch.io and Discord providers

**Files:**

- Produces:
  - **Steam:**
    - Config: `pub struct SteamConfig { pub app_id: u32, pub key_env: &'static str /* publisher Web API key */, pub identity: String /* default "hearth" */, pub reject_banned: bool /* default true */ }`.
    - Body: `{"ticket": "<hex>"}`, where the hex is at most 4096 characters, or else `BadRequest`.
    - Call: `GET https://partner.steam-api.com/ISteamUserAuth/AuthenticateUserTicket/v1/?key=..&appid=..&ticket=..&identity=..`.
    - OK means `response.params.result == "OK"`, which yields `namespaced("steam", steamid)`. When `reject_banned` is set, `publisherbanned` or `vacbanned` being true gives `Rejected("banned")`. `response.error` gives `Rejected(errordesc)`.
    - The Steam key never appears in any log line or error message, because errors are built only from response fields.
  - **itch.io:**
    - Body: `{"api_key": "<key>"}`.
    - Call: `GET https://itch.io/api/1/jwt/me` with `Authorization: Bearer <key>`.
    - A 200 with `user.id` gives `namespaced("itch", id)` and the display name `display_name`, falling back to `username`. An `errors` array or a 401 gives `Rejected`.
  - **Discord:**
    - Config: `pub struct DiscordConfig { pub client_id: String, pub secret_env: &'static str, pub redirect_uri: Option<String> }`.
    - Body: `{"code": "<code>"}`.
    - First call: `POST https://discord.com/api/oauth2/token` (form: `client_id`, `client_secret`, `grant_type=authorization_code`, `code`, plus `redirect_uri` when configured).
    - Second call: `GET https://discord.com/api/users/@me` with the bearer access token. That gives `namespaced("discord", id)` and the display name `global_name`, falling back to `username`. The access token is thrown away and never stored.
  - Shared rules for all three:
    - A 5xx, a timeout, or a body that is not JSON gives `Upstream("<provider> unavailable")`.
    - A 4xx from the upstream gives `Rejected`.
    - A token is issued only from the OK branch (Review Focus 4).

```
rooms            = ccu / room_size
msgs_per_player  = min(intents_per_sec, 20)            # SDK batching cap
ws_msgs          = ccu * msgs_per_player * S            # S = seconds_per_month
ticks            = rooms * hz * S                        (ticked only; one alarm request per tick)
connects         = ccu * sessions_per_player_day * 30
do_requests      = ws_msgs / ws_incoming_ratio + connects + ticks
worker_requests  = connects + connects                  # auth + connect upgrade per session
room_msg_rate    = room_size * msgs_per_player
active_fraction  = event:  min(1, room_msg_rate * idle_hibernate_after_s)
                   ticked: 1
gb_s             = rooms * active_fraction * S * memory_gb
rows_written     = event:  rooms * room_msg_rate * S    # one state row per handler pass
                   ticked: rooms * (hz / persist_every_ticks) * S
storage_gb       = rooms * state_kb / 1e6
billable(x)      = max(0, x - included); usd = billable / 1e6 * usd_per_million   (storage: billable * usd_per_gb_month)
total            = workers.base_usd_month + Σ usd
```

  - CLI: `hearth cost --ccu <n> --room-size <n> --intents <per sec> [--ticked <hz>] [--persist-every <ticks, default 20>] [--state-kb <default 4>] [--sessions <per player per day, default 2>] [--pricing <file>] [--json]`. It prints a table with the columns `ITEM QUANTITY BILLABLE USD`, the total, `prices as of <as_of>`, and the assumptions. With `--json`, it prints the `Estimate` as JSON. Inputs that are ≤ 0 (except `intents`, which may be 0) exit with code 2 and a message naming the flag.

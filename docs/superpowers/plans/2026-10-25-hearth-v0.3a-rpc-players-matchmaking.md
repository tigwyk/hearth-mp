# Hearth v0.3a (RPC, Player DO, Matchmaking) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rooms and other Hearth objects call each other with typed RPC (`ctx.call`, plus a durable fire-after-commit `ctx.notify`). Per-player data lives in a Player DO that the player can read at `GET /me`. A Matchmaker hands out room names (quick-join with seat reservations, pools, region hints) and serves a lobby listing of open rooms. Both SDKs gain `quick_join` / `list_rooms` / `get_me`.

**Architecture:** A new `Service` trait is the socket-less sibling of `Room`: persisted `State`, timers and SQL, driven by `on_call`. Every object is reached at the internal path `/__hearth/call` with a MessagePack envelope that carries the caller and the call chain. The chain lets a reentrant cycle fail fast instead of deadlocking on the adapter's mutex. `ctx.notify` writes to a durable outbox table in the same commit as the state. The outbox is delivered after the pass, retried on the alarm, kept in order per target, and deduplicated by the receiver's inbox. Room reports (registry in v0.2c, matchmaker here) move onto this outbox. The Matchmaker is a built-in `Service` with one instance per `(room_type, region)`.

**Tech Stack:** As before. No new crates.

**Spec:** [`Hearth a Rust framework for Durable Object game servers.md`](../../../Hearth%20a%20Rust%20framework%20for%20Durable%20Object%20game%20servers.md), sections Architecture, Room lifecycle step 1, Server API (`ctx.call`), and Persistence. **Builds on:** [v0.1](2026-10-25-hearth-v0.1-event-rooms.md), [v0.2a](2026-10-25-hearth-v0.2a-reconnect-godot-codegen.md), [v0.2b](2026-10-25-hearth-v0.2b-unity.md) and [v0.2c](2026-10-25-hearth-v0.2c-admin.md). Names this plan does not redefine are as defined there.

## Global Constraints

- All earlier Global Constraints still apply.
- The Matchmaker mints room names with a location hint from the first player's region (spec lifecycle step 1). Use the v0.1 continent → hint map, and the region key `"any"` when no continent is known.
- Per-player data lives in a Player DO keyed by player ID and outlives any match (spec).
- `ctx.call::<T>(id, rpc)` is typed DO-to-DO RPC (spec).
- **Additions and deviations:**
  - **`ctx.notify` is added.** A call that fires after commit and is durable, so a match result is never lost when the handler later fails or the target is briefly down.
  - **No separate Lobby DO class.** The lobby is a listing served by the Matchmaker from the open-rooms table it already keeps. A second DO would have to mirror that table. A live, chatty social lobby is just a `Room`.
  - **`GET /me` is read-only.** Clients change their player data only through rooms or services the dev writes.
- Shortcuts, each with a code comment:
  - One Matchmaker DO per `(room_type, region)`: shard by pool when a pool outgrows a single DO.
  - Quick-join only, with no skill or rating matching: add queue-based matching when a game needs it.
- Room names minted by the Matchmaker have the form `m_<region>_<16 hex>`. Room names that the private `POST /rooms/{type}` mints keep the v0.1 form.
- **Out of scope** (the v0.3b plan): JWT/Steam/itch/Discord auth, gateway IP and player rate limiting, `hearth cost`. Leaderboard DOs stay the dev's own `Service` (spec: "the dev's choice"), and no built-in one is provided.

## Review Focus

1. **Reentrant call cycles.** Room A calls service B, which calls A, while A holds its adapter mutex. It must fail fast with `ReentrantCall`, not hang until the platform timeout. Tests are in Tasks 1 and 3.
2. **Notify when the handler fails, and when the target is down.** A notify from a failed handler is never sent. A notify from a successful handler is applied exactly once, in order per target, even when it is retried after the target was unreachable. Tests are in Task 2.
3. **Players racing for the last seat.** Two quick-joins for one free seat must never both be assigned it. The same player asking twice gets the same room. Tests are in Task 4.
4. **Forged matchmaker rooms and internal paths.** A client connects to a self-made `m_enam_<hex>` name. The Matchmaker must ignore reports from rooms it never minted. `/__hearth/call` is never reachable from outside. Tests are in Tasks 4 and 5.
5. **`/me` leaking other players' data.** It returns only the token holder's own view. No route lets a client address another player's DO. Tests are in Task 5.

  - `#[derive(Serialize, Deserialize)] pub struct Envelope { pub msg_id: Option<String>, pub from: Target, pub chain: Vec<Target>, pub rpc: Value }`. `chain` lists every object currently awaiting in this call path, outermost first. The reply is a MessagePack `Result<Value, CallError>`.
  - `#[derive(Serialize, Deserialize, Debug, thiserror::Error)] pub enum CallError { #[error("reentrant call into {0:?}")] ReentrantCall(Target), #[error("bad rpc: {0}")] BadRpc(String), #[error("{0}")] Handler(String), #[error("unreachable: {0}")] Unreachable(String) }`
  - `pub trait Callable { const BINDING: &'static str; type Rpc: Serialize + DeserializeOwned; type Reply: Serialize + DeserializeOwned; }`
  - `pub trait Service: Callable + Default + 'static { type State: Serialize + DeserializeOwned + Default; async fn on_call(&mut self, ctx: &mut ServiceCtx<Self>, from: &Target, rpc: Self::Rpc) -> Result<Self::Reply>; async fn on_timer(&mut self, ctx: &mut ServiceCtx<Self>, key: TimerKey) -> Result<()> { Ok(()) } }`
  - `pub trait RoomRpc: Room + Callable { async fn on_call(&mut self, ctx: &mut Ctx<Self>, from: &Target, rpc: Self::Rpc) -> Result<Self::Reply>; }`. A room's `on_call` runs as a normal handler pass, so a state change is patched to its clients.
  - `ServiceCtx<S>` has `state(&mut self) -> &mut S::State`, `sql(&self) -> &dyn Sql`, `timer`, `cancel_timer`, `now_ms`, `call`, `notify` (Task 2), and `me(&self) -> &Target`.
  - Both `Ctx` and `ServiceCtx` gain `async fn call<T: Callable>(&mut self, name: &str, rpc: T::Rpc) -> Result<T::Reply, CallError>`. It sends at once and does **not** roll back when the handler later fails; this goes in the doc comment, which also points to `notify`.
  - `pub struct ServiceRuntime<S: Service, H: Host>` with methods `new(host) -> Self`, `async fn call(&mut self, env: Envelope) -> Result<Value, CallError>`, `async fn alarm(&mut self)`, and `async fn inspect(&mut self) -> Result<Option<Value>>`. The state is persisted in `hearth_state` (seq unused, `locked = 0`), and a handler error rolls the state back, as in a room.
  - `RoomRuntime` gains `async fn call(&mut self, env: Envelope) -> Result<Value, CallError>` (requires `R: RoomRpc`, through a separate `impl` block).
  - `Host` gains `fn me(&self) -> Target` and `async fn call(&self, to: &Target, env: Envelope) -> Result<Value, CallError>`. Before sending, the caller sets `env.chain` to its incoming chain plus `me()`. The receiver returns `ReentrantCall(me)` at once when `me()` is already in `env.chain`, before taking any lock.
  - `pub struct TestWorld` with methods `new() -> Self`, `add_room::<R: Room>(&mut self, binding: &str, name: &str) -> RoomRef`, `add_service::<S: Service>(&mut self, name: &str) -> ServiceRef` (binding from `S::BINDING`), `call::<T: Callable>(&mut self, name: &str, rpc: T::Rpc) -> Result<T::Reply, CallError>` (as an external caller with `binding = "test"`), `partition(&mut self, binding: &str, down: bool)` (calls to that binding return `Unreachable`), `advance(&mut self, d)` (shared clock; fires every object's due alarm), `hibernate_all(&mut self)`, `room(&mut self, r: RoomRef) -> &mut TestRoom<_>`, and `service_state::<S>(&mut self, s: ServiceRef) -> Value`. Calls between objects route synchronously through the world. A call to a target that does not exist yet creates it, just as `id_from_name` does.

**Interfaces:**
- Consumes: Task 1.
- Produces:
  - `Ctx::notify<T: Callable>(&mut self, name: &str, rpc: T::Rpc)` and the same on `ServiceCtx`. It is buffered with the other effects and dropped when the handler fails.
  - The tables `hearth_outbox (id TEXT PRIMARY KEY, binding TEXT NOT NULL, name TEXT NOT NULL, body BLOB NOT NULL, attempts INTEGER NOT NULL, next_ms INTEGER NOT NULL, first_ms INTEGER NOT NULL)` and `hearth_inbox (msg_id TEXT PRIMARY KEY, at_ms INTEGER NOT NULL)`.
  - The ID is `"{now_ms:013}-{seq:06}-{me.binding}/{me.name}"` and is unique per sender. It doubles as `Envelope.msg_id`, so the receiver can dedupe it globally.
  - Commit: the outbox rows are inserted in the same synchronous block as the state save, with no `await` between them. Check against the pinned `worker` version that the DO SQL API makes writes without an intervening `await` atomic (output gate or write coalescing). If it exposes `transaction_sync`, wrap both writes in it.
  - Delivery: after each pass, and on the internal timer `"h:outbox"`, for each target in order of its oldest pending ID, send that target's rows in ID order. Stop at the first failure for that target, so later rows wait and per-target order holds. On success, delete the row. On failure, set `attempts += 1` and `next_ms = now + min(1000 << attempts, 300_000)`, and set `"h:outbox"` to the minimum `next_ms`. When `now - first_ms > 86_400_000`, log `{"hearth":"outbox_dropped",...}` and delete the row, so the outbox stays bounded.
  - Receiver: when `env.msg_id` is `Some(id)` and `id` is already in `hearth_inbox`, reply `Ok(Value::Null)` without running the handler. Otherwise run the handler, and insert the ID in the same commit as its state change, but only when the handler succeeds. Prune rows older than 24 h on each insert.
  - Reports: the v0.2c `RoomReport`s are now `ctx.notify::<RegistryService>("global", report)` effects that the runtime issues itself. This happens only when a `HEARTH_REGISTRY` binding is present, through `Host::has_binding(&self, b: &str) -> bool`. They are no longer best-effort.

  - The instance name is `"{room_type}:{region}"`, and the service parses it from `ctx.me().name`.
  - Tables: `mm_rooms (name TEXT PRIMARY KEY, pool TEXT NOT NULL, capacity INTEGER, players TEXT /*JSON array*/, locked INTEGER, metadata TEXT, minted_ms INTEGER, updated_ms INTEGER)` and `mm_reservations (player_id TEXT PRIMARY KEY, room TEXT NOT NULL, until_ms INTEGER NOT NULL)`.
  - `QuickJoin` algorithm:
    1. If the player is already in some `mm_rooms.players`, or holds an unexpired reservation, return that room.
    2. Otherwise pick the room in `pool` that is not locked and has `capacity - |players ∪ unexpired reservation players| > 0`, preferring the fewest free seats (fill rooms first) and then the oldest.
    3. If there is none, mint `m_<region>_<16 hex>`, insert it with `capacity` taken from the RPC, and reserve. Taking capacity from the RPC means two simultaneous quick-joins land in the same new room before any report arrives. Later reports overwrite `capacity`.
    4. Reserve: insert or replace `(player, room, now + 30_000)`.
  - `Report` for a name not in `mm_rooms` is **ignored** (Review Focus 4). `Players` with an empty list keeps the row until `Disposed`. `Disposed` deletes the row and its reservations.
  - `List` returns the open rooms in `pool` that are not locked and have free seats > 0, sorted like `QuickJoin`, with `limit` clamped to 1..=50.
  - The pool comes from `QuickJoin`, so the matchmaker records it at mint time; the room never needs to know its pool.
  - `matchmaker_object!()` defines `HearthMatchmaker` through `#[hearth::service]`.

### Deliberate deviations

**Scope**

- **Task 7 (Unity) is deferred.** The user asked for the next plan that needs no
  Unity toolchain; v0.2b is still unimplemented and Task 7 extends its API.
- No separate Lobby DO and quick-join only, as the plan's shortcuts say.

**Server and RPC**

- **`Callable` is macro-generated, not a supertrait.** `Service` and `RoomRpc`
  declare `Rpc`/`Reply`; the `#[hearth::service]` and `#[hearth::room(…, rpc)]`
  macros emit the `Callable` impl and the DO wrapper.
- **`Host::me` is not a host method.** The runtime owns its `Target` (binding
  from the macro, name learned from `hearth_meta`) and `Ctx::me`/`ServiceCtx::me`
  return it with no host round-trip; `Host::report` was removed as planned.
- **Outbox identity.** Rows are `INTEGER PRIMARY KEY AUTOINCREMENT` with the
  `msg_id` derived at delivery (`{first_ms}-{id}-{binding}/{name}`) rather than
  the plan's TEXT primary key: same ordering and dedupe key, no extra index.
- **The `Disposed` report is delivered before the wipe** (queue, flush, then
  wipe), because a disposed room has nothing left to retry from; every other
  report is an ordinary outbox row retried on the alarm.
- **Reports are gated by `Host::has_binding`**, so a room in a deployment
  without a registry or matchmaker binding writes no outbox rows at all.
- **Roster reports are sorted by player id**, so a live→held seat change on
  reconnect does not reorder the roster and send a spurious report.
- **Outbox backoff reaches the 5 minute cap** at the ninth retry
  (`min(1000 << attempts, 300_000)`); the earlier shift clamp stopped at 256 s.
- The single DO alarm is shared: `h:outbox` carries retries.

**Player data and the gateway**

- **`PlayerRoute` carries only the binding.** The plan's `view: fn(&Value) -> Value`
  and the `PlayerEnvelope<R>` blanket are unnecessary: a player service
  implements `PlayerService::client_view` and its DO answers the internal
  read-only `GET /__hearth/view`. The dev's own `Rpc` type stays untouched, and
  `/me` can only ever name the token's own player id.
- **`registry_object!`** keeps `/list` by wrapping `ServiceObject<RegistryService>`
  and delegating the alarm to it.

**Matchmaker**

- **`open_rooms` filters `locked = 0`** in the shared query, so quick-join and
  the lobby exclude locked rooms with one rule.
- **A stale reservation is dropped when its room filled up**, so the SDKs'
  ROOM_FULL retry (`POST /match` again) gets matched into another room instead
  of the same full one for the rest of the 30 s window.
- **Matchmaker reports are wrapped as `{"Report": …}`** because `MmRpc` is
  externally tagged, while the registry still takes the bare `RoomReport`.
  Both matchmaker bugs were found by the Task 4 tests, not by the e2e.
- The instance name is `{room_type}:{region}`, and a name without a region is
  `any` — what a localhost gateway produces (no `request.cf`), so the e2e's
  forged-room check uses `m_any_<hex>`.

**Testing harness**

- **`TestWorld` is a new harness beside `TestRoom`**, not a rewrite: the
  v0.1/v0.2 suites keep `TestRoom`, the object-to-object tests use `TestWorld`
  (`add_room`, `add_rpc_room`, `add_service`, `call::<S>(name, rpc)` by instance
  name, `sql_of`, `set_matchmaker`, `partition`).
- **`hearth-test` has a dev-dependency on `hearth-matchmaker`** so the report
  tests drive the real service in-process; test-only edge.
- The registry report tests use a test-local `TestRegistry` in `hearth-test`
  instead of depending on `hearth-admin`.

**Docs, sample and commit shape**

- Stale spots a docs review flagged were fixed in the Task 5 commit: the README
  room example (old `serve` signature, missing `max_clients`), `docs/admin.md`'s
  "same list passed to serve" wording, and the matchmaking page's locked-room
  note (written before the lock filter landed).
- The CLI template keeps `player: None, matchmaker: false` and no
  player/matchmaker classes in its `wrangler.toml`: generated projects opt in.
- **Commit shape.** Task 4's commit also carries the `PlayerService` trait and
  its re-exports, because they live in files Task 4 has to touch anyway
  (`service.rs`, both `lib.rs` maps) and splitting them would leave a
  non-compiling intermediate commit. The rest of the player path (worker object,
  macro flag, gateway, sample, docs) is Task 5's commit.
